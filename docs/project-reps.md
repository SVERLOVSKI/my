# Reps — трекер практики

Мини-проект для этого репозитория. Цель — отработать основные темы раздела Learn из
[карты React](./react-roadmap.md) руками. Основной проект использует `useState`, Context
и `localStorage`; reducer изучается в [отдельном упражнении](#отдельное-упражнение-reducer).
Дополнительные API из справочника и темы async остаются в роудмапе для отдельного изучения.

## Что это

Приложение, в котором ты ведёшь собственную практику: алгоритмические задачи, темы React,
что решено, что завалено, что пора повторить. То есть ты пользуешься им, пока его пишешь —
это единственный надёжный способ не бросить пет-проект на третьем этапе.

Ключевая механика — **повторения**. Через 3 дня (ровно 72 часа) после последней успешной
попытки задача появляется в списке «пора повторить». Этот список нигде не хранится — он
каждый раз вычисляется из истории попыток и текущего времени.

**Без бэкенда.** Данные сохраняются в `localStorage`, начиная с этапа 8.

**Состояние в React.** Задачи хранятся в `useState`, а `localStorage` сохраняет их между
перезагрузками. На этапе Context общий state и обработчики действий переезжают в `BoardProvider`.
Ввод в формах и другие локальные состояния остаются в своих компонентах.

## Доменная модель

```ts
type Topic = 'algorithms' | 'react' | 'typescript' | 'css'
type Difficulty = 'easy' | 'medium' | 'hard'
type Status = 'backlog' | 'in-progress' | 'done'

type Attempt = {
  id: string
  date: string        // ISO
  minutes: number
  solved: boolean
  note: string
}

type Task = {
  id: string
  title: string
  topic: Topic
  difficulty: Difficulty
  status: Status
  sourceUrl?: string   // ссылка на LeetCode / доку
  attempts: Attempt[]
  createdAt: string
}
```

Счётчики, «пора повторить» и статистика за неделю **вычисляются** из этих данных,
а не хранятся рядом. Состояние незавершённой сессии добавляется отдельно на подшаге 8.1.

## Правила повторений и статистики

**Повторения:**

- Дата выполнения — `date` последней по времени успешной попытки (`solved: true`).
- Задача попадает в «Сегодня», когда с этой даты прошло не менее 72 часов.
- Она остаётся в списке до следующей успешной попытки. После неё новый срок — ещё 72 часа.
- Неудачная попытка не меняет срок и не убирает задачу из списка.
- Смена `status` не меняет дату выполнения и срок повторения.
- Задачи без успешных попыток в список повторений не попадают.

**Статистика:**

- Период — последние 7 календарных дней, включая сегодня, в локальном времени браузера.
- Минуты по дням — сумма `minutes` всех попыток за соответствующий день, независимо от `solved`.
- Разбивка по темам — сумма минут этих же попыток, сгруппированных по `topic` задачи.
- Процент решённых — доля задач со статусом `done` среди всех задач доски.
  При пустой доске процент равен 0. Этот показатель считается по всем задачам, без ограничения
  семью днями.

## Экраны

1. **Доска** — задачи тремя колонками по статусу, фильтры по теме и сложности, поиск.
2. **Задача** — модалка с деталями и историей попыток; с подшага 8.1 — таймер и сохранение
   результата сессии как попытки.
3. **Сегодня** — что пора повторить; с подшага 8.1 — также текущая сессия с таймером.
4. **Статистика** — минуты по дням, разбивка по темам, процент решённых.

«Доска», «Сегодня» и «Статистика» — вкладки, переключение через обычный state.
Детали задачи открываются в модалке. Роутинг в основной план не входит.

## Этапы

Каждый этап или его подшаг — отдельный коммит. Не переходи дальше, пока предыдущий не работает.
«Читать» — страницы из [карты](./react-roadmap.md), которые нужно открыть **перед** кодом.

### Этап 1. Статика и JSX

Читать: Your First Component, Importing and Exporting, Writing Markup with JSX, JavaScript in JSX.

Свёрстанный на Tailwind каркас: шапка, три колонки, пример карточки задачи. Тексты пока
заданы прямо в JSX; массив данных и его вывод появятся на этапе 2. Никакого state.

Приёмка: каркас и пример карточки рендерятся, каждый компонент лежит в своём файле,
`npm run build` проходит.

### Этап 2. Пропсы и композиция

Читать: Passing Props, Conditional Rendering, Rendering Lists, Keeping Components Pure.

Добавить массив из 6 задач в `src/data/seed.ts` по доменной модели. Корневой компонент
передаёт данные в `TaskCard`, `Badge`, `Column`, `EmptyState` через пропсы. Карточка рисует
бейдж сложности цветом, у задачи без попыток — плашка «не начата». Колонка без задач
показывает `EmptyState` через `children`.

Приёмка: все 6 задач отображаются в соответствующих колонках по одному разу. Вложенные
компоненты получают данные пропсами и не импортируют массив. Ключи не по индексу;
пустая колонка показывает `EmptyState`.

### Этап 3. События и первое состояние

Читать: Responding to Events, State: A Component's Memory, Render and Commit, State as a Snapshot, `useId`.

Добавить поиск по заголовку, фильтры по теме и сложности, переключатель «только незавершённые»
(`status` не равен `done`). Все условия применяются совместно.

Форма добавления задачи — controlled inputs, `useId` для связки `label` и `input`.
Задачи, значения фильтров, поисковый запрос и поля формы управляются через `useState`;
отфильтрованный список вычисляется при рендере. Поля формы остаются локальными.

Приёмка: поиск и каждый фильтр работают отдельно и в сочетании; при отсутствии совпадений
показывается пустое состояние. Форма добавляет одну задачу за отправку, ничего не мутируется.

### Этап 4. Иммутабельные обновления

Читать: Queueing a Series of State Updates, Updating Objects in State, Updating Arrays in State.

Смена статуса задачи, удаление, редактирование заголовка, добавление попытки в `attempts`.
Для добавления попытки достаточно кнопки с заранее заданными `minutes` и `solved`, текущей
датой и пустым `note`. Форма ввода результата сессии появится на подшаге 8.1.

Здесь же — сортировка списка через `toSorted` по `createdAt`: новые задачи сверху.

Приёмка: каждая операция изменяет только выбранную задачу; добавление попытки увеличивает
её `attempts` на одну запись. Исходные массивы и объекты не мутируются, сортировка не меняет
порядок исходного массива.

### Этап 5. Подъём состояния, детали и вкладки

Читать: Reacting to Input with State, Choosing the State Structure, Sharing State Between Components, Preserving and Resetting State.

#### Подшаг 5.1. Общее состояние и модалка задачи

Задачи и выбранная задача нужны доске, модалке и будущим вкладкам: найти их ближайшего общего
родителя и поднять общее состояние туда. Поиск и фильтры из этапа 3 хранятся в общем родителе
их элементов управления и списка. Если состояние уже расположено у нужного родителя,
достаточно проверить передачу пропсов.

Добавить открытие модалки для выбранной задачи и кнопку закрытия. Показать заголовок, тему,
сложность, статус, ссылку `sourceUrl`, если она есть, и историю попыток: дату, минуты,
результат и заметку. Если попыток нет, показать пустое состояние.

Хранить `selectedTaskId`, а саму задачу находить в общем массиве при рендере. Модалка получает
`key={task.id}`, чтобы её локальное состояние сбрасывалось при переключении задачи.
Счётчики задач по статусам в шапке вычисляются из того же массива.

Приёмка: модалка открывается для нужной задачи и закрывается кнопкой; изменение данных задачи
отражается и в карточке, и в деталях. При выборе другой задачи история соответствует ей.
Нет копии выбранной задачи в state; счётчики в шапке обновляются после действий из этапа 4.

#### Подшаг 5.2. «Сегодня» и «Статистика»

Добавить переключение вкладок «Доска», «Сегодня», «Статистика» через state. На «Сегодня»
показать задачи для повторения по правилам выше и возможность открыть их детали.
На «Статистике» — минуты по дням, минуты по темам за 7 дней и процент решённых задач.

Обе вкладки используют общий массив задач. Расчёты — обычные функции; список повторений
и агрегаты вычисляются при рендере. В расчёт повторений передаётся текущее время, чтобы
проверять границу 72 часов без ожидания трёх дней. Таймер появится на подшаге 8.1.

Приёмка: до истечения 72 часов задача отсутствует в повторениях, ровно через 72 часа появляется.
Неудачная попытка не меняет результат; успешная убирает задачу ещё на 72 часа. Задачи без
успешных попыток отсутствуют. Для статистики проверены границы семидневного периода,
попытки с обоими значениями `solved` и пустая доска. Переключение вкладок сохраняет задачи.

### Этап 6. Context и useState

Читать: Passing Data Deeply with Context.

`BoardProvider` хранит общие данные доски в `useState` и раздаёт их вместе с обработчиками
`addTask`, `moveTask`, `renameTask`, `removeTask`, `logAttempt`. Обработчики используют
функциональные обновления `setTasks`, когда новое значение зависит от предыдущего.
Отдельно — `ThemeContext` (светлая/тёмная тема через Tailwind `dark:`).
Хук-обёртка `useBoard()` с понятной ошибкой, если провайдера нет.

Приёмка: задачи имеют один источник состояния в `BoardProvider`; вложенные компоненты
получают общие данные и действия через `useBoard()`. Пропсы, передававшиеся через промежуточные
компоненты только ради вложенных потребителей, убраны; там, где хватало `children`, контекст
не появился. Поля форм остаются локальными.

### Этап 7. Refs и DOM

Читать: Referencing Values with Refs, Manipulating the DOM with Refs.

Автофокус поля при открытии формы через ref-колбэк, скролл к только что добавленной задаче.
Ref передаётся как обычный проп (React 19, без `forwardRef`). Для скролла DOM-узел должен
уже существовать после коммита обновления задач.

Приёмка: поле получает фокус при появлении формы; добавленная задача, подходящая под текущие
фильтры, прокручивается в область видимости. `ref.current` не читается и не записывается
во время рендера.

### Этап 8. Эффекты и кастомные хуки

Читать: Synchronizing with Effects, Lifecycle of Reactive Effects, Separating Events from Effects, Removing Effect Dependencies, Reusing Logic with Custom Hooks.

Сохранение в `localStorage` (`useLocalStorage`), дебаунс поиска (`useDebounce`), горячие
клавиши (`useHotkeys`). Хуки выделяются для состояния и эффектов; расчёты повторений
и статистики остаются обычными функциями.

Чтение сохранённых задач при запуске и последующее сохранение используют то же состояние
доски: второй копии массива задач в отдельном хуке или компоненте нет. Сохранение не должно
перезаписывать данные начальными задачами до чтения ранее сохранённого массива.

Поисковое поле обновляется сразу, фильтрация по запросу — после 300 мс без нового ввода.
Клавиша `/` переводит фокус в доступное поле поиска, если пользователь не вводит текст
в другом поле. Escape закрывает открытую модалку. Обработчики клавиатуры снимаются
при размонтировании, отложенный поиск отменяется при изменении запроса и размонтировании.

Приёмка: после перезагрузки восстанавливаются сохранённые задачи, включая пустой массив.
Поиск применяет последний запрос после паузы 300 мс; горячие клавиши не мешают вводу
в полях. Очистка есть у эффектов, создающих подписки и отложенные действия; запись
в `localStorage` сама по себе очистки не требует. Предупреждения линтера про зависимости
не подавлены комментариями.

#### Подшаг 8.1. Таймер сессии

Выполнять после этапов 7 и 8: здесь одновременно нужны refs, эффекты и их очистка.

**Поведение:**

- Таймер — секундомер для выбранной задачи. Действия: запуск, пауза, продолжение,
  завершение и отмена.
- Одновременно существует одна незавершённая сессия. Пауза сохраняет её; перед запуском
  другой нужно сохранить результат или отменить текущую.
- Время начинается с нуля, на паузе не увеличивается, продолжение сохраняет накопленное время.
- Закрытие модалки и переключение вкладок сохраняют сессию. В модалке её задачи и на вкладке
  «Сегодня» отображается одна и та же сессия.
- Перезагрузка страницы сбрасывает незавершённую сессию. В `localStorage` сохраняются задачи
  и записанные попытки; незавершённая сессия туда не попадает.
- Удаление задачи отменяет связанную с ней сессию.

**Связь с попыткой:**

- Завершение останавливает отсчёт и фиксирует время завершения. Пользователь указывает
  результат (`solved`) и необязательный `note`, затем сохраняет попытку.
- Сохранение добавляет ровно одну запись в `attempts` соответствующей задачи через
  `logAttempt`. Пустая заметка допустима.
- `id` — новый уникальный идентификатор, `date` — момент завершения в ISO, `minutes` —
  суммарное время работы без пауз, округлённое вверх до целой минуты.
- Сессия с нулевым временем не сохраняется. Любое положительное время до 60 секунд
  включительно даёт 1 минуту; больше 60 и до 120 секунд включительно — 2 минуты.
- После сохранения сессия завершена, повторное нажатие не создаёт дубль. Отмена удаляет
  незавершённую сессию без добавления попытки.
- Статус задачи автоматически не меняется. Успешная попытка запускает новый срок повторения
  по общим правилам, неудачная на него не влияет.
- Добавление попытки кнопкой из этапа 4 остаётся самостоятельным действием; таймер
  передаёт в обработчик результат своей сессии.

**Технические требования:**

- Состояние сессии имеет один источник в `BoardProvider`, выше модалки и вкладок.
  Сброс локального состояния модалки через `key` не сбрасывает общую сессию.
- Продолжительность вычисляется по временным отметкам начала и пауз. Интервал только
  обновляет отображение: количество его срабатываний не используется как прошедшее время.
  Задержки браузера в фоновой вкладке не должны терять время работающей сессии.
- Логику интервала выделить в `useInterval`; его идентификатор хранить в ref.
  Значения для отображения обновляются через состояние React, без чтения ref в рендере.
- На паузе, после завершения, отмены, удаления задачи и при размонтировании интервал очищается.
  Продолжение создаёт один интервал. Повторный запуск эффектов в `StrictMode` не оставляет
  дополнительных интервалов.
- Заголовок браузерной вкладки отражает текущую сессию; после её сохранения или отмены
  и при размонтировании восстанавливается обычный заголовок.

Приёмка: проверены запуск, пауза и продолжение без сброса и учёта времени паузы; границы
0, 60 и более 60 секунд; сохранение с обоими результатами и пустой заметкой; повторное
нажатие сохранения и отмена без записи попытки. Закрытие модалки, смена вкладки приложения
и работа в фоновой вкладке не теряют сессию. Удаление её задачи отменяет сессию,
перезагрузка сохраняет записанные попытки и сбрасывает незавершённую сессию.
После размонтирования и повторных запусков эффектов нет оставшихся или дублирующихся интервалов.

### Этап 9. Рефакторинг «You Might Not Need an Effect»

Читать: You Might Not Need an Effect (перечитать целиком).

Проверить все `useEffect`: «пора повторить», статистика и отфильтрованный список — производные
значения, они уже должны считаться при рендере. Если для них появились эффекты, убрать их.
Этап остаётся проверкой архитектуры и не требует предварительно добавлять ненужные эффекты.
`useMemo` добавлять для вычислений, стоимость которых подтверждена измерением.

Приёмка: эффектов осталось столько, сколько реально синхронизируется с внешним миром
(localStorage, таймер, заголовок документа, клавиатура). Остальное считается при рендере.

### Этап 10. Полировка

Читать: Your UI as a Tree, `memo`.

Измерить ввод в поиск в React DevTools Profiler на одном и том же наборе задач и запросе.
Если обнаружена проблема, применить `memo` там, где измерение показало пользу, и сравнить
длительность коммитов до и после. Если проблемы нет, добавлять `memo` не требуется.
Доступность: фокус-стили, `aria-label`, работа с клавиатуры. Адаптив на Tailwind.

Приёмка: клавиатурой можно переключить вкладки, добавить задачу, открыть и закрыть её детали,
управлять сессией и сохранить попытку. Фокус виден, у элементов управления есть доступные имена.
Для проверки поиска записаны набор данных, запрос и результат профилирования; при оптимизации
сравнены измерения до и после. Визуальные проверки, ручные сценарии в браузере и профилирование
выполняет Иван.

Небольшая форма попытки: поля `minutes`, `solved`, `note`, предварительный просмотр
и кнопка сброса. Все данные упражнения локальны.

1. Сделать форму на `useState`: ввод → предварительный просмотр → возврат к редактированию.
   Просмотр доступен только при положительном числе минут; сброс очищает поля и возвращает
   форму к вводу.
2. Перенести переходы в чистую функцию `attemptFormReducer` и подключить `useReducer`.
   Описать действия `field/changed`, `review/opened`, `editing/resumed`, `form/reset`
   дискриминированным юнионом `Action`. Сравнить обработчики до и после переноса логики.
3. Разнести поля, предварительный просмотр и кнопки по компонентам. Внутри упражнения
   передать состояние и `dispatch` через отдельные контексты состояния и действий.

Приёмка: поведение формы сохранилось; reducer лежит в отдельном файле, не мутирует state
и не выполняет побочных эффектов. Ручные проверки подтверждают изменение поля, запрет
просмотра при неположительном числе минут, возврат к вводу и полный сброс. Компоненты
упражнения получают состояние и `dispatch` из своих контекстов.

## Правила игры

- **Пишешь руками.** ИИ — только для объяснений и ревью, не для генерации кода.
- **Коммить по этапам и подшагам** с осмысленным сообщением.
- **Не забегай вперёд.** На этапе 3 достаточно `useState` и пропсов. Сначала освой подъём
  состояния, затем на этапе 6 добавь Context для общих данных. Reducer изучается в отдельном
  упражнении; в основном проекте остаётся `useState`.
- **Не подключай библиотеки.** Ни стейт-менеджера, ни UI-кита, ни `date-fns`, ни `uuid`
  (`crypto.randomUUID()` уже есть в браузере). Единственное исключение — роутер, если после
  10-го этапа захочется.
- **Каждый этап заканчивается зелёным** `npm run build` и `npm run lint`.

## Альтернативы, если не зайдёт

Ту же карту тем закрывают: тренажёр флеш-карточек с интервальным повторением,
конструктор опросов с предпросмотром, или клиент к публичному API (фильмы, покемоны) с
избранным и пагинацией. Reducer можно освоить тем же отдельным упражнением, а refs
потребуют подходящей задачи в выбранном проекте.
